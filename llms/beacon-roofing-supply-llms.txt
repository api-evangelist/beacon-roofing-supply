## Authentication

- V2/V3/Public/Internal: OAuth 2.0 bearer token, `Authorization: Bearer <token>`.
- V1: cookie session (JSESSIONID, DYN_USER_ID, DYN_USER_CONFIRM, siteId), established by POST /login.
  Session lasts 1 hour, or 7 days with the RememberMe flag.
- Only the refresh_token grant is published. The INITIAL grant is not documented publicly — credentials
  are issued during partner onboarding.
- `scopes` on the token endpoint is a refresh-behaviour selector (empty | "all" | "refresh_token"),
  NOT a permission scope. Authorization is enforced server-side by permission template; call
  GET /getCurrentUserPermission to discover what a token may do.
- Multi-site: most operations take `apiSiteId`, resolved query string > root of request body > the
  site bound to the token's client_id.

## Things an agent must know before calling this API

- NO IDEMPOTENCY. Zero occurrences of "idempoten" across all 424 operations. POST /submitOrder places
  a real material order against a contractor's account and a retry may place a second one.
- NO ORDER CANCELLATION. There is no cancel, void or amend operation for a submitted order anywhere in
  the contract. Beacon's own docs route cancellation through a branch representative, and document
  that `checkForAvailability` should always be "No" so a human at the branch receives the order.
- NO RATE LIMIT SIGNAL. No 429 is declared on any operation and no RateLimit-*/Retry-After header
  appears in any document or on any live response. The license terms prohibit "excessive or abusive
  usage" without naming a number.
- 419 MEANS EXPIRED. 154 operations return HTTP 419 for an expired bearer token. 419 is not an IANA
  registered status code. Treat 419 as refresh-and-retry and 401 as re-authenticate; they are distinct.
- 405 IS OVERLOADED. 376 operations declare 405 as both "wrong method" and "this API is not available"
  for your site. A 405 is not necessarily a client error.
- ERROR ENVELOPE: { success, messages: [{key, code, type, value}], result }. A numeric message-code
  registry (1XXX request params, 2XXX profile, 3XXX specified params, 4XXX system, 5XXX response) is
  published inside info.description. 27 named V2 operations return the raw payload with NO envelope.
- Every error response carries an undocumented top-level `traceId` — quote it in support tickets.
- PAGINATION: pageNo/pageSize, with a shared BCPaginationDataObj envelope
  (next, previous, pageSize, currentPage, totalCount, results). Placement is inconsistent — query on
  most operations, path on 7.
- REHEARSAL PATHS EXIST: GET /getCurrentOrderReview and GET /validateOrderByLocation let you check an
  order before submitting it. Use them.

## What Beacon/QXO does NOT publish

Verified absent by probe on 2026-09-04, not merely unfound:
- No MCP server (hosted or stdio), no A2A agent card, no llms.txt, no ai-plugin.json.
- No /.well-known document of any kind on any host. www.qxo.com answers 200 with an HTML SPA shell
  for unmatched /.well-known paths — those are soft-404s, not documents.
- No status page (status.beaconproplus.com does not resolve; /status 404s). An authenticated
  Health Check tag exists inside the V2 contract, which is not the same thing.
- No SLA, no security.txt, no vulnerability disclosure programme, no trust center, no published
  certifications.
- No first-party SDK in any package registry, no CLI, no Postman collection, no GitHub organization.
- No AsyncAPI and no outbound webhooks. Notifications are polled via GET /getNotifications.
  POST /quickMeasure/callback is Beacon RECEIVING a report from GAF, not Beacon emitting an event.
- The published Swagger UI is deliberately read-only: its loader nulls out Try-It-Out, the authorize
  button and the server selector.
